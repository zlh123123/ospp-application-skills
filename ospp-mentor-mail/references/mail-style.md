# Mail Style

## Goal

Write an email a busy open-source mentor can scan quickly and answer concretely. Sound like the applicant, not a marketing template.

## Subject

Include `OSPP`, the project name or ID, and the purpose when useful.

Examples of useful shapes:

- `OSPP 2026 项目咨询：<项目名称>`
- `回复：OSPP 2026 <项目编号> 技术方案确认`
- `跟进：OSPP 2026 <项目名称> 申请咨询`

Do not add urgency, praise, or status claims to the subject.

## Body

- Use the verified form of address; when uncertain, use a neutral greeting rather than inventing a title.
- Put identity and purpose in the first two sentences.
- Mention only the experience that explains readiness for this project.
- Prefer one or two concrete repository findings over a list of technologies.
- Ask only questions whose answers change the plan.
- Keep attachments and signature factual.
- Preserve the user's established signature format when one is provided.

Prefer connected paragraphs. Use a numbered list only when there are several independent questions that the mentor should answer separately.

## Tone Check

Remove any sentence that performs politeness without adding meaning. Keep ordinary courtesy: greeting, a brief request, thanks, and closing are enough.

Replace vague claims:

| Avoid | Prefer |
| --- | --- |
| 我对该方向有浓厚兴趣 | 我已阅读项目要求并定位到仓库中的 `<module>` |
| 我具备扎实的技术基础 | 我在 `<project>` 中完成过 `<relevant work>` |
| 希望得到您的宝贵指导 | 想确认该项目是否使用 `<dataset/baseline>` |
| 我一定能够按时完成 | 按当前拆分，前 `<period>` 完成 `<verified scope>` |

Do not manufacture repository findings merely to make the email concrete.

## Pre-Send Review Checklist

Before handing the draft back to the user, flag whether the recipient came from user input, every intended attachment exists and is the intended version, and the subject and body are internally consistent. For replies, verify that the thread context is unambiguous. This checklist does not send the message.
